## 1. 원인 태그·통계 (PR #41, `329e74c`)

"가장 많이 틀린 원인 Top 5"를 검토자 대시보드에 넣었다. 로드맵 「F5·F6 다음 기능 순서」 4번이다.

- **원인은 새 판단이 아니다.** 이미 저장된 판정 JSON의 결정적 단계(`verdict.decisive`의 `step`·`rule_seq`)와 막힌 방향의 사유를 묶어 이름만 붙인다. 그래서 **DB 표·열 변경이 0**이다.
- 태그 9개: ACL 규칙에서 차단 / ACL 암묵적 deny / 경로 없음 / 기본 게이트웨이 없음 / 다음 홉 없음 / 호스트가 전달하지 않음 / 라우팅 루프 / 막는 곳 없음(통과) / 분류 못 함. 방향(정방향·복귀)은 태그를 쪼개지 않고 행 안에 `복귀 N건`으로 적는다.
- 분모는 `comparison=DISAGREE`(받은 답 ≠ NetProof 판정). `AGREE`·답 없음·비교 불가는 제외하고 **제외 수를 화면에 적는다**. 상한 2,000건을 넘으면 "최근 2,000건만 집계"를 표시한다.
- 설계 때 확인한 것: 엔진이 내는 차단 사유는 고정 문자열 5개 + ACL 2가지뿐이라 **정상 저장된 DENY는 전부 분류된다**(`분류 못 함`은 옛·깨진 JSON에서만).

리뷰에서 2건을 고쳤다.

| | 지적 | 고친 방법 |
| --- | --- | --- |
| R1 | **판정하지 못한 사례**(UNSUPPORTED·INVALID)에도 `원인: 분류 못 함 · 정방향`이 떴다. 추적한 적 없는 방향을 사실처럼 적는다 | 결과가 PASS·DENY일 때만 표시 |
| R2 | 원인 줄이 「받은 답」과 「판정」 패널 **사이 빈 바닥**에 떠 있고, 판정 패널의 문장과 중복됐다 | 판정 카드 제목으로 이동(`판정 · 원인 태그(통계): …`). 공유 부품 `ResultPanel`은 건드리지 않음 |

R1은 QA 합성 사례 5건이 모두 PASS/DENY라 화면 확인에서 걸리지 않았다. 리뷰에서 임시 환경에 판정 불가 사례를 만들어 재현했다.

## 2. pfSense 상태 추적 계산 1단계 (PR #44, `b050348`)

수업에서 쓰는 pfSense를 계산할 수 있게 엔진을 넓혔다(이슈 #40 요구사항 2).

- **핵심**: 상태 추적은 **복귀 패킷의 규칙 평가만 건너뛰고 경로 계산은 건너뛰지 않는다.** 복귀 경로가 없으면 상태가 있어도 DENY다(`synthetic-02`를 고정 회귀로 둠).
- 입력은 pfSense 화면과 1:1인 구조화 필드다. `stateful: true` 장비의 인터페이스에 `rules_in`(동작·프로토콜·출발지·목적지·포트)과 `default_in`. 기존 ACL 문법으로 치환하지 않고, 일치 계산만 기존 `acl.py`를 재사용한다(새 파서·새 숫자 변환 없음 — 이슈 #7·#9 재발 방지).
- **이슈 #40의 「같은 서브넷 통신」 경계는 이미 충족이었다.** 모든 것을 막는 방화벽을 같은 링크에 둬도 `172.16.50.2 → .10`은 PASS이고 ACL 단계가 아예 없다. 코드 0줄로 맞아서 회귀 테스트로 고정만 했다.
- 화면은 이번 범위가 아니다(D2). `web/` 변경 0줄이고, 지금은 엔진과 `POST /api/verify`로만 쓸 수 있다.

리뷰에서 1건을 고쳤다.

| | 지적 | 고친 방법 |
| --- | --- | --- |
| R1 | 복귀 패킷이 **상태 없는** 상태 추적 장비를 지날 때 `default_in`만 보고 `DENY`·`PASS`를 단정했다. 그 장비의 상태 테이블을 모르는데 단정하는 것이고, 같은 상황의 ICMP 응답은 이미 판정 불가라 비일관이었다 | 복귀 추적 중 상태 없는 장비를 만나면 **프로토콜·규칙·기본 정책과 무관하게 판정 불가** |

**이 지적의 원인은 Claude의 설계 문장이었다**("비대칭 복귀 경로의 다른 장비는 규칙을 평가한다"). 사용자가 정한 D4보다 약한 문장이어서 Codex는 설계대로 구현했을 뿐이다. 설계 문장·`docs/semantics.md` §14·구현·테스트를 한 커밋에서 같이 고쳤다.

부수 변화 하나를 확인했다. 방화벽 **자신이 출발지**인 session은 인바운드 상태가 생기지 않아 `DENY` → `UNSUPPORTED`가 됐다. 실제 pfSense는 자기가 연 연결에 상태를 만들므로 DENY 단정이 잘못이던 자리이고, 같은 흐름을 `one-way`로 두면 PASS라 pfSense → Graylog(syslog) 같은 단방향 흐름은 그대로 계산된다.

## 4. 검증 방법 (오늘 실제로 한 것)

- **독립 A/B 대조**: 병합 전 엔진을 `git show`로 임시 폴더에 복원해 별도 프로세스로 돌리고, 새 기능을 쓰지 않는 입력의 **전체 verify 사전**을 비교했다. pfSense 1단계에서 두 시드 각 3,000건, **불일치 0**. 기존 판정이 한 건도 달라지지 않았다는 근거다.
- **실브라우저 확인**: 원인 태그는 임시 SQLite QA 서버 + Chromium으로 1280×800·375×812에서 가로 넘침 0·콘솔 오류 0을 확인했다. R1 재현에는 QA 시드에 없던 판정 불가 사례를 더한 **저장소 밖 하네스**를 썼다.
- **병합 뒤 운영 확인**: 원인 태그는 공개 주소 번들 해시가 리뷰 때 직접 빌드한 파일과 같은지로, pfSense는 `POST /api/verify`에 상태 추적 장비를 보내 응답이 바뀌는지로 확인했다(배포 전 `PASS` → 배포 후 `UNSUPPORTED`).
- Codex가 적은 테스트 수와 Claude가 직접 실행한 수는 **네 번 모두 같았다**.

## 7. 오늘 배운 것

- **설계 문장이 약하면 구현도 정확히 그만큼 약해진다.** pfSense R1은 Codex의 실수가 아니라 Claude가 쓴 한 문장이 사용자 결정(D4)보다 약했던 결과였다. 리뷰에서 코드만 보지 않고 설계 문장까지 돌아본 덕에 잡혔다.
- **사용자가 추천을 뒤집은 쪽이 옳았다.** "모르면 차단"은 그럴듯했지만, 실제 장비의 자동 규칙과 기존 상태를 못 보는 모델이 DENY를 단정하면 확신에 찬 오답이 된다. "모르면 판정 불가"가 이 프로젝트의 정체성과 맞다.
- **합성 QA 데이터가 모두 정상 경로면 경계 결함을 못 본다.** 원인 태그 R1은 QA 사례 5건이 전부 PASS/DENY라 Codex의 화면 확인을 그대로 통과했다. 리뷰에서 없는 상태를 일부러 만들어야 보였다.
- **같은 숫자를 양쪽이 따로 실행해 맞춰 보는 게 값싸고 강하다.** 네 번 모두 일치했고, 어긋났다면 그것부터 봤을 것이다.
