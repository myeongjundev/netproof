# 1부. 검증 품질

코드 자체는 상태가 좋다. 구멍은 **"엔진을 믿을 근거"를 자동으로 만들어 내지 못한다**는 쪽에 있다.

## 1-1. 실제 결과로 대조된 사례가 0건이다 `[사람]`

가장 큰 구멍이고, LLM이 대신할 수 없는 유일한 항목이다.

2026-10-11 보완 측정: [Batfish 교차 검증 도구](batfish-diff.md)를 엔진0.2.0·고정 시드20261010·각 모양40개로 직접 실행했다(`python scripts/batfish_diff.py`, 별도 pybatfish venv/고정 Docker digest). 83구성×20통신=1660건의 PASS/DENY는 모두 같았고, DENY 단계1511건 중44건은 잘못된 다음 홉에서 엔진 `send`와 Batfish `NEIGHBOR_UNREACHABLE`→`route`가 달랐다. 제외0·201.25초·종료1이며 불일치 JSON/설정을 보존했다([HANDOFF](../HANDOFF.md)). 엔진은 수정하지 않았고 불일치 분석은 별도 과제다. **독립 계산기와의 교차 검증이며 실제 장비 대조를 대신하지 않는다.**

**측정**
- `cases/` 3개 전부 `source`가 "합성 사례(Workbench 초안, 실제와 무관)"다.
- 사례 JSON에 `actual`(실제 장비 결과) 필드 자체가 없다. 키는 `id · title · source · network · flow · claim · expect`뿐이다.
- `/api/dashboard`는 `confirmed_in_scope` · `agree` · `ai_wrong`을 **이미 정확히 계산한다**(`server/netproof_api/cases.py`). 파이프는 완성됐고 데이터만 0이다.

**판단**
제품 정체성은 "계산으로 검증하고, 실제 결과로 그 검증까지 검증하는 실습실"인데, 정작 엔진이 실제와 대조된 적이 한 번도 없다. `plan.md`의 검증 전략 4단계(기준 사례)와 5단계(실습망 스캔 대조)가 비어 있고, Definition of Done의 "실제 사례 10건 이상"도 0건이다. 4주차 사용자 테스트에서 보여 줄 일치율이 지금은 계산 자체가 불가능하다.

**할 일**
1. 동기 실습에서 실제 결과(ping·접속·Nmap 캡처)가 있는 사례를 모은다.
2. 사례 JSON에 `actual` 필드를 더할지, 게시판의 "실제 결과" 입력만 쓸지 정한다 → 정해지면 `[Claude]`가 설계로 옮긴다.

**먼저 할 30초짜리**
강사님께 **"수업 실습 방화벽이 Cisco ACL인가 pfSense인가"**를 묻는다. pfSense(상태 기반)면 엔진의 무상태 ACL 모델(ADR-005)과 의미가 달라 일치율 자체가 무의미해진다(`plan.md` Risk 2). 사람 트랙에 아직 미해결로 남아 있는데, 답 하나로 품질 리스크가 사라지거나 범위를 다시 잡게 된다.

## 1-2. 퍼징이 일회용으로 버려진다 `[Codex]`

**측정** — 조사 중 퍼저를 만들어 직접 돌렸다.

```
수정 전 엔진(8c7ee35, 0.1.2) · 무작위 입력 4,000회
  → 계약 위반 134건, 서로 다른 경로 2가지
     [133회] ValueError: '①'  at  seq = int(tokens.take("순번"))
     [  1회] ValueError: '①'  at  icmp_type = ... int(icmp)      (verify.py:38)

수정 후 엔진(0.1.3) · 같은 퍼저 4,000회
  → 계약 위반 0건
     (PASS 84 · DENY 580 · UNSUPPORTED 1,160 · INVALID 2,176 — 네 판정에 고르게 들어간다)
```

퍼저가 이슈 #7을 **두 경로 모두 몇 초 만에 독립적으로 재현**했다. 설계 문서가 꼼꼼한 읽기로 찾아낸 `verify.py:38`까지 기계가 스스로 짚었다.

**판단**
`HANDOFF.md` 리뷰 기록에 따르면 PR #6 재리뷰 때도 무작위 ACL 줄 4,739개로 퍼징했지만 "임시 테스트, 지움"으로 끝났다. 그래서 이슈 #7은 **운 좋게** 발견됐고, 지웠으니 같은 종류의 다음 버그는 못 잡는다. 지금 엔진 테스트 105개는 전부 사람이 고른 입력이라, 아무도 생각 못 한 입력에 대해서는 아무것도 보장하지 않는다.

**이슈 #9가 이 판단을 다시 증명한다.** PR #8이 병합된 직후, 같은 계약을 깨는 경로가 또 나왔다 — `('9' * 5000).isdecimal()`은 참이지만 `int()`는 4300자리 한도(`sys.get_int_max_str_digits()`)에 걸려 `ValueError`를 낸다. #7과 **같은 종류, 같은 네 경로**다. 사람이 한 번에 한 원인씩 찾아 고치는 방식으로는 이 종류가 끝나지 않는다는 뜻이다.

다만 정직하게 적는다 — **처음 퍼저는 #9를 잡지 못했을 것이다.** 생성기의 이상 토큰 목록에 아주 긴 숫자가 없었기 때문이다. 퍼저의 가치는 "무작위"가 아니라 **생성기가 극단값을 포함하는지**에 달려 있다.

그래서 생성기에 `"9" * 4301` 같은 긴 숫자를 넣고 **현재 `main`(`a716341`, #9 미수정)에 다시 돌려 확인했다**:

```
engine 0.1.3 · 4,000회 → 계약 위반 155건
  ValueError: Exceeds the limit (4300 digits) for integer string conversion: value has 5000 digits
  위치: seq = int(tokens.take("순번"))
```

고친 생성기는 #9를 스스로 찾아낸다. 다만 이 실행은 네 경로 중 **순번 경로 하나만** 때렸다 — 긴 토큰이 포트·ICMP 자리에 떨어지려면 더 돌리거나 자리별로 비중을 줘야 한다. 그러므로 퍼저는 *종류*를 지키는 그물이고, **경로별 고정 테스트는 따로 있어야 한다**(이슈 #9 작업 정의의 네 경로 테스트가 그 역할이다).

`verify()`의 독스트링은 이미 계약을 선언하고 있다 — *"어떤 입력에도 예외 대신 네 값 중 하나를 돌려준다"*. 이 계약을 **상시 테스트로** 바꾸면 이슈 #7 한 건이 아니라 그 **종류 전체**가 막힌다. Hypothesis는 이미 설치돼 있다(`engine/pyproject.toml`).

**할 일**
`engine/tests/test_fuzz_contract.py` 한 개. 유효한 사례에서 출발해 한 번에 한두 곳만 변형하고, 결과가 항상 네 값 중 하나인지만 본다. 아래 부록의 생성기를 그대로 쓰면 된다.

**완료 조건**
- 새 테스트가 **이미 아는 버그 두 개를 모두 잡는지**를 직접 확인한다. 둘 다에서 실패하지 않으면 그 테스트는 아무것도 지키지 않는 것이다.
  - `8c7ee35` 체크아웃(이슈 #7 수정 전) → 실패해야 한다
  - `a716341` 체크아웃(이슈 #9 수정 전) → 실패해야 한다
- 두 수정이 모두 들어간 현재 엔진에서 통과하고, 전체 엔진 테스트가 기준선 + 새 테스트로 통과한다.
- 실행 시간은 2초 안쪽으로 둔다(`max_examples`로 조절). 느려지면 CI에서 아무도 안 돌린다.

## 고칠 것

### 2-1. 색 역할이 충돌한다 `[Claude 설계 → Codex]`

`--accent`(라이트 `#1f5f5b` 틸 / 다크 `#6fc2b9` 민트)가 브랜드·주요 동작 색인데, `--pass`(`#1e6b3a` 초록)와 **같은 계열**이다. 제품의 전체 메시지가 "통과냐 막힘이냐"인데 브랜드 색이 통과 색을 잠식한다. 다크 모드에서 특히 심하다 — 화면에서 가장 밝은 민트 덩어리가 "판정하기" 버튼이라 통과처럼 읽힌다.

대비 문제가 아니라 **의미 충돌**이다. 유채색은 pass/deny/warn에만 주고 `--accent`는 중립(슬레이트·남색)으로 빼는 쪽을 권한다. 토큰 1개 변경이지만 화면 전체에 영향이 가므로 설계로 먼저 정한다.

### 2-2. 판정하기 버튼이 결과 카드의 머리처럼 보인다 `[Codex]`

꽉 찬 바(`.judge .primary { width: 100% }`)가 판정 패널 바로 위에 붙어 있어 버튼이 아니라 카드 헤더로 읽힌다. 게다가 화면에서 가장 진한 색이 "결과"가 아니라 "버튼"이다. 위계가 거꾸로다.

### 2-3. 좌우 비중이 거꾸로다 `[Codex]`

`styles.css:46` — `grid-template-columns: minmax(0, 1.15fr) minmax(0, 1fr)`. **입력이 결과보다 넓다.** 강사님 피드백 ③(시각화가 강점)을 받아들인 제품이라면 증거 쪽이 넓어야 한다. 최소한 뒤집어 `1fr 1.2fr`.

### 2-4. 상자에 위계가 없다 `[Codex]`

`--radius: 10px`에 더해 하드코딩 `8px`가 20군데 흩어져 있다. 장비 입력 상자·판정 카드·ACL 근거·사례 저장이 전부 같은 테두리, 같은 모서리, 같은 무게다. 중요도가 다른데 시각적 가중치가 같다. 판정 카드만 확실히 띄우고 나머지는 눌러야 한다.

### 2-5. 같은 증거가 두 번 나온다 `[Claude 설계]`

`access-list 101 deny tcp …` 문장이 "가는 길" 홉 안에 한 번, "ACL 근거" 블록에 또 한 번 — 거의 같은 모양(모노스페이스 + 붉은 배경)으로 반복된다. 둘은 역할이 다른데(홉 증거 / ACL 전문) 생김새가 같아서 "같은 걸 왜 두 번 보여주지"로 읽힌다. 어느 쪽을 줄일지는 설계 판단이 필요하다.

### 2-6. 타이포 스케일이 없다 `[Codex]`

12 · 13 · 14 · 15 · 16 · 17 · 18 · 20 · 22 · 26 · 28 · 30px — 11가지 크기가 필요할 때마다 찍혀 있다. 5단계로 정리하고 토큰으로 뺀다.

### 2-7. 토폴로지 그림이 없다 `[Claude 설계]`

입력하는 동안 자기가 만든 망이 어떻게 생겼는지 볼 수 없다. 경로 스트립은 판정 **후에만**, 그것도 1차원이다. 네트워크 도구의 가장 큰 시각적 공백이고 강사님 피드백 ③의 핵심인데 로드맵 5주차에 있다 — **앞당길 후보**다.

### 2-8. 접근성 잔손질 `[Codex]` — 각 1줄

- **`<h1>`이 앱 전체에 없다**(axe 위반, moderate). 브랜드가 `<a class="brand">`이고 패널은 전부 `<h2>`다.

# 부록. 퍼저 (1-2의 재료)

조사에 쓴 생성기를 줄여 옮긴다. 핵심은 **유효한 사례에서 출발해 한 번에 한두 곳만 변형**하는 것이다.
처음에 완전 무작위로 만들었더니 4,000회가 전부 `INVALID`로 걸러져 엔진 안쪽에 닿지 못했다.

```python
ODD = ["²", "①", "٣", "４４３", "½", "〇", "💥", "", " ", "\t", "　",
       "-1", "0x50", "65536", "nan", "NULL",
       "9" * 4301, "9" * 5000, "0" * 4301,   # int() 4300자리 한도 (이슈 #9)
       "1" * 100, "a" * 4000]                # 길이 자체가 깨뜨리는 경로
WORDS = ["permit", "deny", "remark", "ip", "tcp", "udp", "icmp", "any", "host",
         "eq", "neq", "lt", "gt", "range", "established", "log", "echo",
         "access-list", "10", "443", "10.0.0.2", "0.0.0.255", "object-group"]

def rand_line(rnd):          # 대부분 진짜 규칙 모양, 25%만 이상한 토큰
    return " ".join(rnd.choice(ODD) if rnd.random() < 0.25 else rnd.choice(WORDS)
                    for _ in range(rnd.randint(1, 8)))

# 흐름: 유효한 flow에서 1~2개 필드만 교체 (src/dst/proto/mode/포트/icmp)
# 구성: 60% ACL 줄 교체 · 20% 인터페이스 필드 · 15% 경로 · 5% 키 제거

assert verify(net, flow)["result"] in ("PASS", "DENY", "UNSUPPORTED", "INVALID")
```

변형 비율이 중요하다. 위 비율로 4,000회를 돌렸을 때 PASS 84 · DENY 580 · UNSUPPORTED 1,160 · INVALID 2,176으로 네 판정에 모두 들어갔고, 그래야 ACL 해석과 경로 조회까지 실제로 검사된다.

| 5 | **투명성 페이지 "엔진을 믿어도 되나"** | 판정 규칙 요약 · 테스트 수 · 퍼징 계약 · 실제 사례 일치율 공개 | 작음 | "Verify before you trust"를 사이트가 실천. 2·3번 작업(퍼징·CI)의 숫자가 그대로 쓰인다 |
| 6 | **증거 리포트 내보내기** | 판정·경로 그림·ACL 근거를 한 장 PDF/PNG로 | 중간 | 과제·보고서 첨부. 링크 공유(P1)의 짝 |
| 7 | **첫 화면 30초 데모** | 처음 온 사람에게 예시가 자동 판정되며 "AI 답 ≠ 계산"을 보여 줌 | 작음 | 사용자 테스트의 첫 10초 |
| 8 | **내 기록** | 내 사례 · 내 예측의 오탐·미탐 · 많이 틀린 원인 | 중간 | 로드맵의 연습 문제 모드와 이어져 다시 올 이유 |
| 9 | **"나도 재현됨" 확인** | 남의 사례에 "내 실습에서도 같은 결과" 한 번 | 작음 | 실제 결과 데이터가 늘어난다. `plan.md`가 **댓글은 제외**했으므로 반응을 증거 쪽으로 받는다 |
| 10 | **API·CLI 안내 페이지** | `/api/verify` 사용법 · 명령줄 판정 · 사례 JSON 형식 | 작음 | 보안 개발자 청중에게 "도구로도 쓸 수 있다" |

**우선순위**: 사용자 테스트 전 1·7·3 → 발표 숫자 2·5(3주차 오탐·미탐 대시보드와 같은 데이터) → 정책 검증 뒤 4 → 여유를 보며 6·8·9·10.
**미리 정할 것** `[사람]`: 2번은 AI 출처를 **고르는 목록**으로 받아야 집계된다(자유 입력이면 같은 AI가 여러 이름으로 흩어진다). 4번은 강사 역할이 새로 생기므로 ADR이 필요하고, 강사님이 실제로 쓸지 먼저 묻는 것이 좋다.

## 3-6. Codex에게 묻는 것
