# NetProof 판정 의미론 v0

엔진을 만들기 전에 "무엇을 PASS라고 부르는가"를 문장으로 고정한다. 테스트는 이 문서를 기준으로 쓴다.
이 문서와 코드가 다르면 코드가 틀린 것이다(문서를 먼저 고치고 코드를 맞춘다).

## 1. 판정 대상

- 판정 대상은 **구체적인 흐름 하나**다: 출발지 IP · 목적지 IP · 프로토콜(tcp/udp/icmp) · 포트 또는 ICMP 종류.
- 결과는 네 값 중 하나다.
  - `PASS` — 모델 안에서 계산한 결과, 흐름이 통과한다.
  - `DENY` — 모델 안에서 계산한 결과, 흐름이 막힌다. 막힌 장비·단계·규칙을 함께 준다.
  - `UNSUPPORTED` — 판정에 필요한 요소가 지원 범위 밖이다. **추측하지 않고 멈춘다.**
  - `INVALID` — 입력 자체가 성립하지 않는다(주소 형식 오류, 중복 IP 등).

## 2. 통신 가능의 뜻 (ADR-005)

- 기본 모드는 `session`: **정방향과 복귀 방향이 모두 통과해야** PASS다.
  - TCP 복귀 패킷은 출발지·목적지와 포트를 뒤집고 ACK가 켜진 패킷으로 본다.
  - ICMP `echo`(8)의 복귀는 `echo-reply`(0)다. 그 밖의 ICMP는 `one-way`만 지원한다.
  - UDP 복귀는 주소와 포트를 뒤집은 UDP 패킷이다.
- `one-way` 모드는 정방향만 본다(예: syslog처럼 응답이 없는 흐름).
- ACL은 **무상태**다. 정방향이 허용됐다고 복귀가 자동으로 허용되지 않는다.
  상태 기반 방화벽(pfSense 등)은 §14(ADR-016)의 별도 입력 모델로 다룬다. 그 지원 범위를 벗어난 조건은 판정 불가로 기록한다.

## 3. 링크 가정

- 서로 다른 장비의 인터페이스가 **같은 서브넷(네트워크 주소와 접두사 길이가 같음)이면 같은 링크에 연결돼 있다**고 본다.
- VLAN·트렁크·스위치·ARP는 모델 밖이다. 같은 서브넷인데 실제로는 다른 VLAN이라 통신이 안 되는 사례는 범위 밖이다.

## 4. 호스트

- 호스트는 패킷을 만들고 받기만 한다. 다른 장비의 패킷을 전달하지 않는다.
- 목적지가 자기 인터페이스 서브넷 안이면 링크로 바로 보낸다. 아니면 **기본 게이트웨이**로 보낸다.
- 기본 게이트웨이가 자기 서브넷 밖이면 `INVALID`, 게이트웨이가 없으면 `DENY`(게이트웨이 없음)이다.
- 호스트 방화벽은 모델 밖이다.

## 5. 라우터

패킷이 라우터 인터페이스로 들어오면 아래 순서를 따른다.

1. **들어온 인터페이스의 ACL in** — 위에서부터 첫 번째로 일치한 규칙의 동작을 따른다. 어떤 규칙에도 일치하지 않으면 **암묵적 deny**다. ACL이 붙어 있지 않으면 통과다.
2. 목적지가 라우터 자기 인터페이스 주소면 라우터가 받는다(전달 끝).
3. **경로 조회** — 직접 연결 경로(인터페이스 서브넷)와 정적 경로 가운데 **가장 긴 접두사**를 고른다. 길이가 같으면 직접 연결이 이긴다. 일치하는 경로가 없으면 `DENY`(경로 없음)이다.
   - 정적 경로의 다음 홉은 직접 연결 서브넷 안에 있어야 한다. 아니면(재귀 조회) `UNSUPPORTED`.
4. **나가는 인터페이스의 ACL out** — 1과 같은 규칙.
5. 다음 홉 주소(직접 연결이면 목적지 주소, 아니면 경로의 다음 홉)를 가진 장비를 같은 링크에서 찾는다. 없으면 `DENY`(다음 홉 없음).
6. 같은 장비·같은 인터페이스를 두 번 지나거나 32홉을 넘으면 `DENY`(라우팅 루프)이다.

## 6. ACL 규칙 일치

- 규칙: `동작(permit|deny) 프로토콜 출발지 [출발지 포트] 목적지 [목적지 포트] [established | ICMP 종류]`
- 프로토콜 `ip`는 모든 프로토콜에 일치한다. `tcp`·`udp`·`icmp`는 그 프로토콜에만 일치한다.
- 주소: `any`, `host A`, `A 와일드카드`, `A/길이`. 와일드카드는 연속된 것만 지원한다(아니면 `UNSUPPORTED`).
- 포트 조건: `eq`, `neq`, `lt`, `gt`, `range`. 포트 조건은 tcp·udp 규칙에만 쓸 수 있다.
- `established`는 ACK가 켜진 TCP 패킷에만 일치한다. 정방향 첫 패킷(SYN)은 일치하지 않는다.
- ICMP 종류: `echo`(8), `echo-reply`(0) 또는 숫자.
- 모르는 키워드(`object-group`, `log` 외 옵션, 다른 프로토콜 등)는 `UNSUPPORTED`다. `log`는 판정에 영향이 없어 무시한다.

## 7. 입력 검증 (INVALID)

- 주소·접두사 형식 오류
- 호스트 인터페이스에 네트워크 주소나 브로드캐스트 주소를 씀(/31, /32 제외)
- 서로 다른 인터페이스에 같은 IP
- 한 장비 안에서 인터페이스 서브넷이 겹침
- 인터페이스가 없는 ACL을 가리킴
- 출발지 IP를 가진 장비가 모델에 없음
- 목적지 IP가 모델 안의 어떤 인터페이스에도 없음 → `UNSUPPORTED`(모델 밖 목적지)

## 8. 정책 검증·도달성 매트릭스

`policy_matrix`는 교차 host 장비의 인터페이스 IP 순서쌍 × 서비스를 기존 `verify`로 계산한다.
같은 장비 내부 쌍과 자기 자신은 검사에서 제외한다. 이 기능은 단일 흐름의 PASS/DENY 의미를 바꾸지 않는다.
입력 전체의 status(OK/INVALID), 셀의 result(네 판정), 셀의 policy(의도 비교)는 서로 다른 필드다.

| 조건 | policy | 기존 compare 대응 |
|---|---|---|
| result가 UNSUPPORTED/INVALID | UNDECIDED | 의도 있으면 NOT_COMPARABLE, 없으면 NO_CLAIM |
| 판정 가능한데 의도 없음 | NO_POLICY | NO_CLAIM |
| PASS/DENY가 의도와 같음 | AGREE | AGREE |
| 의도 DENY인데 PASS | EXPOSED | DISAGREE |
| 의도 PASS인데 DENY | BLOCKED | DISAGREE |

UNDECIDED는 의도 유무와 관계없이 미판정을 드러낸다. 우선순위는
EXPOSED > BLOCKED > UNDECIDED > AGREE > NO_POLICY다. 의도를 판정 입력으로 사용하지 않는다.
매트릭스 입력·상한·집계·오류 계약과 측정 한계는 [policy-matrix.md](policy-matrix.md)에 둔다.

## 9. 관측(실제 결과)과 판정의 구분

`observe`는 사람이 붙여넣은 텍스트에서 실제 결과 입력 후보를 만든다. `verify`의 네트워크 판정과는 별개이며 판정·비교를 바꾸지 않는다. 출발지와 실제 실행 여부는 출력으로 확인할 수 없다. 사람이 실행 환경을 확인해 적용·저장하고 검토자가 확인한다.

| 관측 | observed | 입력 후보 |
|---|---|---|
| ping 손실 0%, 받음 ≥ 1 | reply | PASS |
| ping 손실 100% | no_reply | 미정 |
| ping 부분 손실 | partial | 미정 |
| Nmap open | open | PASS |
| Nmap closed | closed | 미정 |
| Nmap filtered 또는 open\|filtered | filtered | 미정 |
| 지원하지 않는 출력 | unknown | 미정·거절 |

무응답과 filtered는 DENY를 증명하지 않는다. closed는 경로 도달을 나타낼 수 있지만 서비스 상태는 모델 밖이다. Nmap 상태의 의미는 [공식 포트 스캔 문서](https://nmap.org/book/man-port-scanning-basics.html)를 따른다. 이 기능은 DENY 후보를 만들지 않으며, 수동 실제 결과 입력은 그대로 유지한다.

ping은 ICMP echo 흐름, Nmap은 단일 TCP/UDP 목적지 포트만 지원한다. 출력의 목적지·프로토콜·포트가 사례와 같아야 한다. 여러 대상·포트, 혼합·불완전 출력은 거절하며, Windows 오류 응답과 0% 손실 통계가 함께 있으면 성공으로 올리지 않는다. 후보 적용은 지역 입력만 바꾸고 저장·확인 해제는 기존 사례 API가 담당한다.

## 10. 오탐·미탐(혼동 행렬)

사용자가 정한 양성은 통신 차단(`DENY`)이다. 이미 저장된 예측과 검토자가 확인한 실제 결과를 교차 집계한다. 새 판정을 만들거나 다시 계산하지 않는다.

| 칸 | 예측 | 실제 | 의미 |
|---|---|---|---|
| TP | DENY | DENY | 맞게 잡은 차단 |
| FP | DENY | PASS | 오탐: 막힌다고 했는데 실제로 통함 |
| FN | PASS | DENY | 미탐: 통한다고 했는데 실제로 막힘 |
| TN | PASS | PASS | 맞게 본 통과 |

예측 출처는 AI 답(`claim.kind=ai`의 `claim.expected`), 사람 예상(`claim.kind=self`의 `claim.expected`), NetProof 판정(저장된 `result`) 세 축이다. 종류 없는 답은 AI·사람 어느 축에도 넣지 않는다. 한 사례가 답 축과 엔진 축에 함께 포함될 수 있으며 축마다 분모가 다르다. 엔진이 `UNSUPPORTED`·`INVALID`여도 확인된 실제와 AI·사람의 유효한 답이 있으면 해당 답 축에서는 비교할 수 있다.

축의 분모는 검토 확인됨 + 실제 PASS/DENY + 그 축의 예측 PASS/DENY를 모두 만족하는 사례 수다. 제외 사유는 미확인(`not_confirmed`), 확인됐으나 실제 미정(`no_actual`), 그 축 예측 없음(`no_prediction`) 순서로 한 번만 센다. 엔진 축의 미지원·입력 오류는 예측 없음이다. 네 칸의 합은 분모, 분모와 세 제외 사유의 합은 전체 사례 수다. 화면에 축별 분모와 제외 건수를 표시하며 분모 0의 비율은 `—`로 표시한다.

이는 받은 답과 엔진 판정을 비교하는 `comparison`과 다른 축이다. `AGREE`·`DISAGREE`에서 오탐·미탐을 유도하지 않는다. 각 칸의 사례 목록은 같은 예측·실제·확인 조건을 AND로 적용하며, 집계와 목록 건수가 같아야 한다. 불일치 미리보기는 최근 20건이고 전체 건수를 별도로 표시한다.

사례 목록의 `actual_mismatch=1`은 저장된 `result`와 `actual_result`가 모두 PASS/DENY이며 서로 다른 사례만 고른다. 검토 확인 여부와 무관하고 다른 조건과 AND로 적용된다. 받은 답 ↔ 계산의 `comparison`과는 다른 축이다. `actual_mismatch=1&confirmed=1` 목록의 `total`은 대시보드의 `mismatches_total`과 같아야 하며, 기존 page 없는 배열 응답에도 같은 필터가 적용된다.

## 11. ACL 점검

`acl_audit`는 흐름·경로·토폴로지와 무관하게 ACL만 계산한다. 점검은 판정이 아니며 PASS/DENY·comparison·policy를 만들거나 바꾸지 않는다. 기존 형태 검사와 ACL 파서를 재사용하고 토폴로지를 로드하지 않는다.

패킷 공간은 IPv4 출발지·목적지 전체, TCP/UDP 출발지·목적지 포트 1~65535, TCP ACK {0,1}, ICMP 종류 0~255이다. 규칙은 닫힌 구간의 곱(상자)들의 합집합이다. `ip`는 TCP·UDP·ICMP 모두, `neq p`는 [1,p-1]과 [p+1,65535], `established`는 ACK=1이다. 포트 조건과 ICMP 종류는 해당 공간과 교차한다. 규칙 경계값 ±1을 전수 조합해 `Rule.matches` 및 줄을 지운 `Acl.evaluate`와 교차 확인한다.

앞 줄을 순서대로 빼 실제로 먼저 잡는 줄만 `by`에 넣는다. 쌍별 포함이 아니라 여러 줄의 합집합을 뺀다. 분류의 우선 순서는 다음과 같다.

1. 처음부터 빈 규칙은 `never_matches`(일치 불가).
2. 앞 줄들이 전부 잡으면, 실제 원인 줄 중 반대 동작이 있으면 `shadowed`(가려짐), 모두 같은 동작이면 `redundant_earlier`(앞 줄 중복).
3. 남은 패킷을 뒤로 흘려 같은 동작 줄들이 전부 잡으면 `redundant_later`(뒤 줄 중복). 끝에 남아도 현재 줄이 deny면 암묵적 deny가 받으므로 같은 분류와 `implicit_deny: true`를 준다. 남은 패킷을 반대 동작 줄이 잡거나 끝의 permit이 필요한 경우 finding은 없다.
4. 계산 한도 초과는 `undetermined`/`limit`. 남은 패킷이 해석 못 한 뒤 줄에 닿으면 `undetermined`/`unread_below`. 이를 문제 없는 줄로 세지 않는다.

첫 해석 불가 줄은 `unread`, 이후 규칙 줄은 `unchecked`이며 점검을 계속하지 않는다. 앞에서 이미 전부 잡히는 줄은 정상 분류할 수 있다. remark는 별도 표시하고 빈 줄은 목록에서 빼되 원래 줄 번호는 보존한다.

permit의 `open`은 출발지 전체·목적지 전체·모든 프로토콜·모든 목적지 포트·모든 ICMP 종류 중 해당 사실만 담는다. `permit ip any any`는 “나머지 전부 허용”이다. 경고·점수·순위를 만들지 않는다. 중복은 이 ACL에서 줄을 지워도 동작이 같다는 뜻이며, 로그용 끝 deny도 포함한다.

한 줄 계산 중 상자는 최대 2,000개, 요청 전체 상자 교차 시도는 최대 300,000회다(다른 프로토콜 쌍도 시도로 센다). 전자는 해당 줄만 점검 못 함으로 두고 다음 줄을 계속하며, 후자는 해당 줄과 남은 모든 규칙을 점검 못 함으로 둔다. 부분 결과를 완전한 결론으로 사용하지 않는다.

2026-10-03 R1 재측정: 기존 0.204629초는 100,000회에 걸려 499줄이 미판단인 시간이었다. 이 값 하나만으로 한도를 정한 근거를 대체한다. 같은 Windows 로컬 PC에서 `worst_case_lines()`의 500줄 합성 최악 사례(겹치는 /16~24·/24~28 접두사, 양쪽 `neq` 포트, permit/deny 교대)를 각 후보 한도로 순차 3회 실행해 `perf_counter` 시간과 `undetermined` 수를 함께 기록했다.

| 1,000,000 | 4.391783 / 4.471092 / 4.344047 | 445 |
| 3,000,000 | 13.548361 / 13.049480 / 13.339442 | 320 |

측정 후보 중 3회 모두 **1.5초 이하**인 가장 큰 값인 **300,000회**를 선택했다(최대 0.589586초). 기존 2초 목표에 여유를 둔다. 이 제한에서도 합성 최악 사례는 끝까지 판정되지 않으며 미판단 486줄을 그대로 반환한다. 측정은 제한이 있는 요청의 시간이지 500줄 완전 계산 시간은 아니다. **모든 구성의 실행 시간 상한 보장은 아니다.** 시간 변화는 환경·부하에 의존하며 테스트는 벽시계 상한을 단정하지 않는다. 한도 외 상자 수·분류·응답은 바꾸지 않았다.

선택 한도의 별도 재현: 겹치지 않는 `permit ip host 10.0.0.%d any` 120줄은 **0.096953초·undetermined 0**, `permit tcp host 10.0.%d.%d any eq 80`(`i // 256`, `i % 256`) 500줄은 **0.508682초·undetermined 0**. 120줄은 회귀 테스트로 고정했다. 선택값 최악 사례 테스트를 다시 실행한 결과는 **0.590387초·undetermined 486**, 해당 회귀와 합쳐 `2 passed in 0.95s`였다.

재현: `cd engine && ../.venv/Scripts/python -m pytest -q -s tests/test_acl_audit.py::test_disjoint_120_hosts_complete_under_request_budget tests/test_acl_audit.py::test_500_line_bounded_measurement`. 후보 비교는 저장소 루트의 Python에서 `runpy.run_path('engine/tests/test_acl_audit.py')['worst_case_lines']()`를 만들고, `audit.MAX_INTERSECTIONS`를 표의 각 값으로 바꿔 `acl_audit({'acls': {'worst': raw}})` 호출 전후의 `perf_counter` 차이를 3회 잰다(소스 파일 변경 없이 프로세스 안에서만 바꿈).

## 12. 수정 후보

수정 후보는 판정·정답·안전 보장이 아니다. 사용자가 목표 PASS/DENY를 직접 고르며 기본값은 없다. 기존 `verify`의 원인 홉을 읽어 ACL 줄 **삽입만** 제안하고, 복사한 구성에 삽입한 뒤 같은 `verify`가 목표 결과를 낸 후보만 반환한다. 입력·DB·장비에는 쓰지 않고 수정한 network도 응답에 포함하지 않는다. 다른 흐름 영향은 계산하지 않는다. 공유 ACL에 붙은 모든 장비·인터페이스·방향을 사실로 표시한다.

정방향 tcp/udp는 `{act} {proto} host S host D eq P`, ICMP는 `{act} icmp host S host D {종류}`다. 복귀 permit은 TCP `permit tcp host D eq P host S established`, UDP `permit udp host D eq P host S`, ICMP `permit icmp host D host S echo-reply`다. 8은 echo, 0은 echo-reply, 나머지는 숫자다. 기존 `_flow_packet`·`_reverse`로 패킷을 얻고 `parse_rule`·`Rule.matches`로 생성 문법을 확인한다. 복귀 줄에는 고정 출발지 포트 50000을 넣지 않는다.

`anchor_before`는 빈 줄을 포함한 원래 입력 목록의 1부터 센 줄 번호이며 null이면 맨 끝이다. 원래 줄 k마다 anchor가 k인 편집을 편집 목록 순서대로 먼저 넣고 원래 줄을 넣는다. 마지막에는 null anchor 편집을 순서대로 붙인다. `insert_at`은 **모든 편집 적용 뒤** 새 목록의 1부터 센 위치다. 중간 결과의 줄 번호는 원래 번호로 되돌리고, 매번 원본에서 이 규칙으로 재구성한다. 화면의 입력 변환은 기존과 같이 빈 줄을 제외하므로 화면 표시 번호는 판정에 보낸 목록 기준이다.

PASS는 현재 ACL drop 앞(암묵적 deny면 끝)에 permit을 넣고 최대 4번 재판정한다. 경로·게이트웨이 등 다른 원인은 수정하지 않는다. DENY는 현재 PASS의 정방향 ACL 통과 홉만 보며 `(acl, rule_line)` 중복을 제외한 앞 8곳에 deny 하나씩 삽입한 후보를 각각 재판정한다. 초과한 홉은 `truncated: true`로 표시한다. 복귀 방향 DENY는 범위 밖이다. 전체 verify 호출 상한은 처음 판정을 포함해 9회(PASS는 최대 5회)다. 삽입 후 ACL 전체가 500줄을 넘으면 `line_limit`; 서버 입력 500줄 상한과 일치한다.

- `INVALID`: 목표 누락·잘못된 목표 또는 예기치 않은 입력 형식. before는 null, problems는 비어 있지 않다.
- `ALREADY`: 현재 판정이 이미 선택한 목표다. 후보는 없다.
- `OK`: 재판정으로 목표가 확인된 후보만 있다.
- `NO_CANDIDATE`: before를 그대로 보존하고 후보 없음 사유를 준다. `not_decidable`(처음 INVALID/UNSUPPORTED), `not_acl_cause`(ACL 아닌 원인), `no_acl_on_path`(정방향 ACL 없음), `edit_limit`(4줄 초과), `reverify_failed`(재판정 실패), `line_limit`(삽입 후 500줄 초과). 후보 없음은 안전하거나 수정 불가능하다는 증명이 아니다.

화면은 목표 변경·재판정·예시 불러오기에 이전 후보를 지우며 늦은 응답을 버린다. 입력만 바뀌면 이전 결과를 표시하고 원래 줄 이동을 막는다. 자동 적용·복사·입력 반영 버튼은 없다. API는 로그인 없이 사용하며 기존 CSRF·64KB 제한·no-store 정책을 유지한다.

## 13. 원인 태그

원인은 저장된 판정의 결정적 단계와 막힌 방향의 사유를 묶은 이름이다. 집계이며 판정·정답이 아니다. `cause(verdict)`는 네트워크를 읽거나 재판정하지 않으며 PASS/DENY·comparison을 만들거나 바꾸지 않는다. 사례 정답(`expect`)도 읽지 않는다.

| 코드 | 화면 이름 | 저장된 엔진 근거 |
|---|---|---|
| `acl_rule` | ACL 규칙에서 차단 | DENY, decisive.step이 acl_in·acl_out, 양의 정수 rule_seq |
| `acl_implicit` | ACL 암묵적 deny(일치 규칙 없음) | DENY, 같은 단계, rule_seq 없음 |
| `no_route` | 경로 없음 | DENY, 막힌 방향의 reason이 경로 없음 |
| `no_gateway` | 기본 게이트웨이 없음 | 같은 자리의 기본 게이트웨이 없음 |
| `no_next_hop` | 다음 홉 없음 | 같은 자리의 다음 홉 없음 |
| `host_no_forward` | 호스트가 전달하지 않음 | 같은 자리의 호스트가 전달하지 않음 |
| `routing_loop` | 라우팅 루프 | 같은 자리의 라우팅 루프 |
| `no_block` | 막는 곳 없음(통과) | result가 PASS |
| `other` | 분류 못 함 | 알려진 근거 없음, 옛·깨진 JSON 포함 |

return이 객체이고 delivered가 false이면 방향은 `return`(복귀 방향), 나머지는 `forward`(정방향)다. 원인과 방향은 별도 값이다. 각 Top 5 행은 복귀 건수를 함께 보인다. 키 누락이나 다른 JSON 형태는 예외 대신 `other`로 두고, 알 수 없는 사유를 추측하지 않는다. UNSUPPORTED·INVALID는 원인 통계 분모에 포함하지 않는다.

사례 상세의 원인 표시는 저장된 결과가 PASS·DENY일 때만 보인다. UNSUPPORTED·INVALID는 원인·방향을 표시하지 않고 기존 판정 불가·입력 오류 설명을 유지한다. 판정 카드 제목에 `판정 · 원인 태그(통계): …`로 분류 이름을 표시하며, 방향은 엔진의 기존 설명·경로에서 확인한다. 태그에 방향을 다시 붙이지 않는다. 분류 못 한 PASS·DENY의 태그는 `분류 못 함`이다.

검토자 전용 `GET /api/dashboard`의 causes는 저장된 `comparison=DISAGREE`(받은 답 ≠ NetProof 판정)만 센다. AI 답과 사람 예상은 한 분모이며, 전체 불일치의 claim.kind별 건수를 별도로 보인다(종류 미정 포함). 실제 결과나 검토 확인 여부는 조건이 아니다. 오탐·미탐은 실제 결과와 비교하는 별도 축이므로 DISAGREE로 유도하지 않는다.

제외는 AGREE·NO_CLAIM·NOT_COMPARABLE로 서로 겹치지 않는다. 전체 불일치(`disagree_total`) + 세 제외 수 = 전체 사례 수다. 알 수 없는 옛 comparison은 비교 불가로 센다. 정상 저장에서 UNSUPPORTED·INVALID는 받은 답이 있으면 NOT_COMPARABLE, 없으면 NO_CLAIM이다(기존 compare 규칙).

불일치 행의 verdict만 읽으며, created_at 내림차순·id 내림차순으로 최근 최대 2,000건을 분류한다. 상한 초과 시 `limited=true`이고 화면에 **최근 2,000건만 집계**를 적는다. 비율 분모(`denominator`)는 실제 집계한 수이며, 전체 불일치와 종류별 수·제외 수는 상한 없이 집계한다. 따라서 상한 초과에도 전체 사례 분할과 최근 표의 비율을 구분할 수 있다.

분류 가능한 원인은 건수 내림차순, 동률은 위 표 순서로 정렬한다. Top 5 이후는 `그 외`로 합치고, `other`는 별도 `분류 못 함` 줄로 표시한다. **Top 5 건수 합 + 그 외 + 분류 못 함 = denominator**다. 분모 0이면 비율은 `—`다. DB 표·열은 추가하지 않고 사례 목록과 POST /api/verify 응답은 그대로다.

## 14. 제한된 상태 추적 방화벽 (ADR-016)

이 절은 내부 실습망의 pfSense에 대응하는 **지원 필드 안의 계산 모델**이다. 실제 pfSense 장비와 대조하지 않았다. 전체 상태 테이블·TCP 핸드셰이크·시간 초과·설정 파일 파싱은 하지 않는다. 1단계는 엔진 계산만이며 화면 입력·실습 결과 대조는 후속이다.

### 입력

```json
{"id": "PFSENSE", "kind": "router", "stateful": true,
 "interfaces": [{"name": "em1", "ip": "172.16.50.1/24",
   "rules_in": [{"action": "pass", "proto": "tcp", "src": "172.31.195.0/24", "dst": "172.16.50.2", "dst_port": "5000"}],
   "default_in": "block"}]}
```

- `stateful`는 불리언이며 true는 router에만 쓴다. 생략·false이면 기존 무상태 ACL 결과가 유지된다.
- `rules_in`은 규칙 객체의 목록이다. 각 규칙에는 문자열 `action`·`proto`·`src`·`dst`가 필요하다. 인터페이스 하나의 규칙은 서버 입력 제한으로 최대 500개다.
- `pass`·`block`, `ip`(모든 지원 프로토콜)·`tcp`·`udp`·`icmp`, IPv4 주소·CIDR·`any`를 지원한다. 선택 `src_port`·`dst_port`는 TCP·UDP에서 1~65535 숫자 하나(문자열 또는 정수)다. 생략·null·`any`는 포트 제한 없음이다. 규칙 번호는 목록 위치(1부터)다.
- 기존 `acl.py`의 Rule·PortMatch 일치 계산을 재사용하지만 ACL 문자열로 치환하지 않는다.
- `default_in`은 `pass`·`block`·`unknown`이며 생략은 unknown이다. **일치 규칙이 없고 정책이 unknown이면 UNSUPPORTED**다. 실제 장비의 기본·자동 규칙을 추측하지 않는다. 사용자가 pass·block을 입력했다면 그 정책으로 계산하고 근거에 사용자 입력임을 적는다.
- 무상태 장비의 구조화 필드, 상태 추적 장비의 acl_in·acl_out 혼용, 잘못된 필드 형태는 INVALID다. 구조화 입력은 지원 필드만 사용한다.

### 계산과 상태

들어오는 인터페이스에서 위에서부터 첫 일치를 사용한다. 미지원 규칙을 만날 때까지 앞에서 일치하지 않으면 UNSUPPORTED다. 이미 앞에서 일치했다면 뒤 규칙은 결과에 영향을 주지 않는다.

`session`은 정방향이 목적지에 도착했을 때만 정방향에서 인바운드 허용을 받은 상태 추적 장비를 복귀 상태 집합에 넣는다. 복귀는 **그 장비에서만** 규칙 평가를 건너뛰며 홉에 `state`·상태로 허용됨을 기록한다. 복귀 추적 중에 상태가 없는 상태 추적 장비를 만나면 프로토콜과 무관하게 판정 불가(UNSUPPORTED)다. 규칙·`default_in`이 명시돼 있어도 기존 연결 상태를 모르므로 차단·허용을 단정하지 않는다. 무상태 장비의 ACL도 계속 평가한다.

**상태는 경로 계산을 건너뛰지 않는다.** 복귀 경로·다음 홉이 없거나 루프이면 DENY다. 같은 서브넷 직접 통신은 방화벽을 지나지 않는다. 상태는 한 verify 호출 안의 합성 왕복에만 존재하고 다른 요청으로 저장되지 않는다.

`one-way`에는 복귀 계산·상태 생성이 없다. 모델에 없는 기존 상태에 의존하는 ICMP 응답·오류(종류가 echo/8이 아닌 패킷)가 상태 없는 상태 추적 장비를 지나면 UNSUPPORTED다. TCP·UDP 입력은 새 통신의 합성 흐름으로만 다루며 기존 연결·TCP 플래그·패킷 시퀀스를 재현하지 않는다.

반환 키는 기존 verify와 같다. 들어오는 규칙 홉은 `firewall_in`, 복귀 상태 홉은 `state`다. 규칙 근거에는 장비·인터페이스·방향·목록 번호·구조화 규칙 원문이 있고, 모델의 실제 장비 미대조 사실을 함께 적는다. 기본 정책 차단과 새 방화벽 단계의 원인 태그는 기존 분류에서 `other`이며 새 통계 분류를 추가하지 않는다.

### 지원하지 않는 조건

복귀 추적 중 상태가 없는 상태 추적 장비를 만나면 프로토콜·규칙·기본 정책과 무관하게 UNSUPPORTED다.

NAT·포트 전달, floating·그룹 규칙, 스케줄·limiter·고급 옵션, reply-to, 자동 생성 규칙(기본 LAN 허용·anti-lockout 포함), 기존 연결 상태, XML 설정 가져오기, IPv6, VLAN·L2, IDS/IPS 탐지 결과는 지원하지 않는다. 관련 조건을 구조화 규칙 또는 경로상 상태 추적 장비의 추가 필드로 입력하면 UNSUPPORTED다. 입력하지 않은 실제 장비 조건의 존재를 엔진이 자동으로 알아낼 수는 없으므로 계산 결과를 실제 pfSense 동작의 보증으로 표시하지 않는다.

실제 pfSense에 맞는 규칙·기본 정책·통신 경로를 확인하고 관측 결과와 대조하는 것은 D5 확인 후 2단계에서 한다.


## 15. 엔진 버전

같은 입력에 대한 엔진 함수 응답(특히 `verify`의 `result`·`decisive`·`reason`)이 달라질 수 있는 변경은 버전을 올린다. 의미 변경은 둘째 자리, 결과가 바뀌는 버그 수정은 셋째 자리를 올린다. 결과가 같은 리팩터·테스트·문서는 올리지 않는다.

저장된 `engine_version`은 사례를 마지막으로 판정한 엔진이다. 버전이 바뀐 배포 뒤에는 `flask rejudge`를 실행한다(`docs/deploy.md` 절차). PR #44의 pfSense 상태 추적 의미 변경은 `0.1.4`로 배포되었고, `0.2.0`은 그 변경을 포함해 재판정 기준을 구분한다.

알려진 불일치가 고쳐지면 strict XPASS로 테스트가 실패한다. 이때 `known_mismatch` 표시만 지우고 사람이 정한 `expect`는 그대로 둔다.
