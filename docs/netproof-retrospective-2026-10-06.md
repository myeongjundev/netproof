# NetProof — 프로젝트 소개와 개발 과정 회고

- 작성 기준일: 2026-10-06
- 대상: 프로젝트를 처음 접하는 사람, 발표 청중, 개발 과정을 정리하려는 작성자
- 성격: 저장소 기록과 사용자 요청을 바탕으로 만든 회고 초안. 개인적인 동기와 느낀 점은 작성자가 직접 확인하고 다듬는다.

## NetProof는 무엇인가

**NetProof는 네트워크 설정에 대해 AI나 내가 예상한 결과를 계산으로 확인하고, 실제 실습 결과와 비교하며 배우는 웹앱이다.**

“이 통신이 된다·안 된다”라는 결론과 함께 어느 경로와 규칙 때문에 그런 결과가 나오는지 보여 준다. 현재 엔진은 지원 범위의 IPv4 라우팅과 무상태 ACL을 계산한다. 계산 결과는 입력된 구성과 모델의 지원 범위에 따른 것이며, 실제 장비의 동작까지 확인했다는 뜻은 아니다.

공개 주소: [NetProof](https://netproof-vert.vercel.app)

프로젝트의 흐름은 다음과 같다.

**입력 → 계산과 설명 → 보안 점검 → 실제 결과 확인 → 통계와 학습 → 다시 입력**

## 1. 어떤 문제를 발견했는가

> 네트워크 수업에서 설정을 보고 “이 통신이 가능할까?”를 판단할 때, AI의 답이나 내 예상만으로는 확신하기 어려웠다. 통신이 막히더라도 방화벽 규칙 때문인지, 경로가 없어서인지, 돌아오는 길에 문제가 있는지 구분할 근거가 필요했다.

초기에는 AI의 판정이 틀릴 가능성에 주목했지만, 실제 비교에서는 더 구체적인 문제를 발견했다.

합성 사례 두 개에서 CLCO의 12개 답과 로컬 Qwen의 4개 답은 모두 NetProof와 판정이 같았다. 그러나 복귀 경로가 없는 사례에서는 두 모델 모두 막힌 단계를 부정확하게 설명했다. 경로 조회에서 멈추는 상황을 특정 인터페이스로 나가다가 막히는 것처럼 표현했다.

따라서 현재 근거로 말할 수 있는 문제는 **결론이 같아도 설명과 근거를 확인할 필요가 있다**는 것이다. 판정의 일치와 원인 설명의 정확성은 따로 확인해야 한다.

이 비교는 합성 사례와 엔진 사이의 비교다. 실제 장비 결과와의 대조가 아니며, 이 결과만으로 AI나 NetProof의 일반적인 정확성을 주장할 수 없다.

근거: [AI 답 비교 기록](prompts/ai-claim-v1-results.md)

## 2. 내가 어떻게 접근했는가

> 답을 확인할 수 있는 계산 규칙과 증거를 만들기로 했다. 라우팅과 ACL의 동작을 명세로 정하고, 통신이 가는 길과 돌아오는 길을 계산하는 엔진을 만들었다. 화면에는 판정과 함께 경로, 결정 단계, 적용된 규칙을 보여 주도록 했다.

앱은 다음 정보를 구분한다.

| 정보 | 의미 |
| --- | --- |
| AI의 답 | 다른 AI에서 받은 통신 가능 여부 |
| 내 예상 | 사용자가 생각한 결과 |
| NetProof 계산 | 입력한 구성과 지원 범위에 따른 엔진 결과 |
| 실제 결과 | 실습에서 사람이 직접 확인한 통신 결과 |

최종 PASS/DENY는 `engine/`에서만 정한다. 서버와 화면은 엔진의 결과를 전달하고 보여 준다. 지원 범위 밖 구성은 `UNSUPPORTED`, 잘못된 입력은 `INVALID`로 이유를 표시한다. 앱 안에 LLM을 넣어 판정하지 않는다.

검증에는 의미론 명세, 단위 테스트, 속성 테스트, 회귀 테스트와 독립 리뷰를 사용한다. 실제 결과와 사례의 기대값은 사람이 정하며, 기존 사례의 기대값을 바꿔 테스트를 맞추지 않는다.

### 내부 네트워크 수업과의 연결

사용자가 제공한 수업 구성도에는 다음 요소가 있다. 주소와 역할은 그림에 표시된 값이며, 실제 연결 성공을 확인한 기록은 아니다.

| 구성 | 그림의 주소·역할 |
| --- | --- |
| Kali | `172.31.195.249`, 실습 트래픽 재현 |
| pfSense WAN / LAN | `192.168.120.129` / `172.16.50.1`, 경계 통신 제어 |
| Flask 게시판 + Wazuh Agent | `172.16.50.2`, 보호 대상 서비스와 호스트 로그 수집 |
| Graylog | `172.16.50.10`, 로그 수집·검색·시각화 |
| Wazuh Manager | `172.16.50.20`, 로그 분석·규칙 기반 탐지 |
| n8n | `172.16.50.30`, 이벤트 알림·대응 흐름 연결 |

수업은 **내부 네트워크 중심**이다. 그림의 인터넷 구름이나 WAN이라는 이름만으로 공용 인터넷 연결을 가정하지 않는다. Cloudflare, Snort·Suricata 표기도 있지만 실제 활성 구성과 사용 방식은 확인이 필요하다.

NetProof에 추가하려는 흐름은 다음과 같다.

**통신 예상 → pfSense 규칙 계산 → 내부 실습에서 실제 통신·로그 확인 → 규칙 변경 후 재비교**

사용자는 pfSense 실습 연동과 앱 계산 확장 둘 다 요청했다. 요구사항은 [이슈 #40](https://github.com/myeongjundev/netproof/issues/40)에 기록했으며, 아직 설계·구현·실습 검증 전이다.

근거: [계획과 ADR](../plan.md), [판정 의미론](semantics.md)

## 3. 어떤 시행착오가 있었는가

> 정상적인 예시가 동작하는 것만으로 앱이 충분히 검증됐다고 볼 수 없었다. 예상하지 못한 입력, 실제 브라우저 동작, 작은 화면, 배포 환경에서 문제가 드러났다.

### 입력 처리 오류

유니코드 숫자와 매우 긴 숫자에서 숫자 변환 오류가 발생했다. 입력 검증과 관련 회귀 테스트를 보강했다. 일반적인 입력만 확인하면 경계 조건을 놓칠 수 있다는 문제가 드러났다.

### 테스트가 놓친 브라우저 동작

QA 서버는 순차 요청 테스트를 통과했지만, 실제 브라우저에서는 빈 연결 하나 때문에 멈췄다. 동시 연결 처리를 적용하고 재현 테스트를 추가했다. 테스트를 통과했다는 사실과 실제 사용 흐름을 확인했다는 사실은 구분해야 했다.

### 학습 화면의 흐름

예시 버튼이 답을 미리 드러내거나, 휴대폰에서 예상 선택 칸이 너무 아래에 나타났다. 전용 실습 화면, 구성 접기, 간격과 문구 조정으로 개선했다. 결과를 정확하게 계산하는 것과 사용자가 그 결과를 이해하기 쉬운 위치에 보여 주는 것은 각각 확인해야 했다.

### 배포 환경의 제약

새 Supabase 프로젝트를 만들 수 없어 기존 프로젝트 안에 NetProof 전용 계정과 스키마를 두는 방식으로 변경했다. 계획한 구성과 실제 사용할 수 있는 환경 사이의 차이를 해결해야 했다.

### pfSense 확장에서 앞으로 해결할 차이

현재 NetProof는 무상태 ACL 기준으로 정방향과 복귀 경로를 계산한다. pfSense는 기본적으로 연결 상태를 추적하고 응답 트래픽을 상태 테이블에 따라 허용할 수 있다. 기존 ACL 계산을 그대로 적용해 pfSense 전체 동작을 지원한다고 표시할 수는 없다.

또한 같은 서브넷·스위치에서 직접 통신하는 호스트의 트래픽은 보통 경계 방화벽을 지나지 않는다. 수업 그림의 게시판과 수집 도구는 모두 `172.16.50.0/24`에 있으므로 실제 경로를 확인해야 한다. NAT·포트 전달이 사용된다면 변환과 방화벽 규칙의 처리 순서도 고려해야 한다.

이 항목은 이미 해결한 시행착오가 아니라 **신규 확장의 설계 과제**다.

기술 근거: [pfSense 방화벽 기본 동작](https://docs.netgate.com/pfsense/en/latest/firewall/fundamentals.html), [방화벽을 지나지 않는 통신](https://docs.netgate.com/pfsense/en/latest/troubleshooting/firewall.html), [NAT와 방화벽 처리 순서](https://docs.netgate.com/pfsense/en/latest/nat/process-order.html)

## 4. 피드백을 어떻게 반영했는가

> 피드백을 통해 기능을 늘리는 것뿐 아니라, 사용자가 사례를 찾고 원인을 이해하는 흐름을 개선했다. 수업에서 실제 사용하는 도구와 환경에 맞춰 요구사항도 수정했다.

| 피드백·확인한 문제 | 반영한 내용 |
| --- | --- |
| 사례를 쉽게 찾아야 한다 | 검색·필터·페이지 기능 |
| 오탐·미탐 확인이 중요하다 | 실제 결과와 비교하는 대시보드 |
| 계산 근거를 시각적으로 보여 달라 | 경로 표시·ACL 규칙 하이라이트 |
| 예상과 계산의 차이를 실패처럼 느끼게 한다 | 중립적인 비교 문장과 근거 안내 |
| 휴대폰에서 실습 흐름이 길다 | 구성 접기·배치·간격 개선 |
| 수업 도구와 연결하고 싶다 | Graylog·Wazuh 보안 로그와 n8n 연동 예시 |
| 수업에서 pfSense를 배우며 내부망으로 실습한다 | pfSense 실습 연동·계산 확장 요구사항 등록 |

오탐·미탐 대시보드에서는 양성을 통신 차단(`DENY`)으로 정의했다. 막힌다고 예상했는데 실제로 통하면 오탐, 통한다고 예상했는데 실제로 막히면 미탐이다. 미확인·미정·미지원은 해당 집계의 비교 조건에 따라 제외하고 제외 수를 표시한다.

이전 기록에는 pfSense가 제외돼 있었지만, 이번 수업 자료와 사용자 요청을 바탕으로 다시 포함했다. 인터넷 공개나 Cloudflare 연동은 pfSense 기능의 필수 조건으로 두지 않는다. 요구사항 등록과 구현 완료를 구분한다.

## 5. 결과적으로 무엇을 배웠는가

> AI를 활용할수록 무엇을 맡기고 무엇을 직접 검증할지 정하는 일이 중요하다는 것을 배웠다. AI가 동의하거나 테스트가 통과했다는 사실만으로 실제 환경까지 확인됐다고 볼 수 없었다. 계산 근거, 재현 가능한 테스트, 실제 실습 결과를 함께 확인해야 했다.

지금까지의 과정에서 정리할 수 있는 배움은 다음과 같다.

1. **결과가 맞는 것과 이유를 정확히 설명하는 것은 별도로 확인해야 한다.** 같은 판정이라도 막힌 단계의 설명은 다를 수 있다.
2. **지원 범위와 한계를 분명히 해야 한다.** 입력된 모델이 다루지 못하는 조건은 판정 불가로 표시해야 한다.
3. **기능의 정확성과 사용자가 이해하기 쉬운 화면은 각각 검증해야 한다.** 엔진 테스트와 실제 화면 관찰이 모두 필요하다.
4. **AI를 쓰는 과정에서도 사람의 판단을 기록해야 한다.** 어떤 제안을 받아들였고 바꿨는지, 그 이유와 결과를 남기는 것이 중요하다.

“실제로 학습에 도움이 됐다”거나 “실제 네트워크와 높은 정확도로 일치한다”는 결론은 앞으로 사용자 테스트와 실습 대조를 통해 확인해야 한다.
